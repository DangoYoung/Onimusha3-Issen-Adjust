# 从零制作《鬼武者3》的一闪帧数 Mod

这份教程用现有的一闪补丁修正版举例，从定义需求、反汇编、验证数据，一直讲到编译和进游戏测试。打开 [补丁源码](../src/Onimusha3.IssenWindow.cpp) 对照阅读。文中给出的行号对应仓库中的源码。

如果你想先动手，直接从「编译和安装」开始。第一次可以先原样编译，确认自己能生成插件，再回头读判定逻辑。

## 1. 先把玩法写成可验证的规则

目标是给**直接一闪**设置最低帧数。以 5 帧为例，原本 1 帧就向前补 4 帧，原本 2 帧就向前补 3 帧。5 帧或更长的窗口照常。招式没有原始窗口时，补丁没有可供扩展的起点。画面里的橙羽织白光和玩家按下攻击键，要依据同一个扩展后的窗口判断。

这里的帧是敌人动作数据里的**动画帧索引**。视频里录到多少画面，还会受游戏更新节奏和录制帧率影响。做比较时，优先观察白光在同一招式的哪个动作瞬间出现。

先定好测试样例。至少选一个确实能触发白光的短窗口招式、一个达到阈值的招式、一个没有对应窗口的动作。前两种最好来自不同敌人，避免只验证同一种实现。

## 2. 认清要分析的文件

- `oni3.exe` 是游戏程序。本教程使用简体中文版 PC `1.0.0.1`，32 位 x86。可在 PowerShell 运行 `Get-FileHash .\oni3.exe -Algorithm SHA256`，本机分析时的结果是 `4F4DA70B6155B8617F0D777E6C28338A70AB314E1C556E25E41151C37B34B5B2`。文件版本号只是线索，同版本号的可执行文件也应对照哈希或指令确认。
- `Image\Enemy` 下的 `.ldt` 保存敌人资源。某段攻击的窗口有多长，可以回到这些资源里的动作表复核。
- 测试环境的游戏根目录使用 32 位 Ultimate ASI Loader `dinput8.dll`。它会加载 `scripts` 中的 `.asi`。`.asi` 是按 DLL 格式编译出来的插件，加载器会调用它导出的 `InitializeASI`。 [Ultimate ASI Loader 项目说明](https://github.com/ThirteenAG/Ultimate-ASI-Loader#writing-plugins)

反汇编时可以用 Ghidra 导入 `oni3.exe` 并运行分析，查看指令、伪代码和交叉引用。交叉引用就是「还有哪些地方调用了这段代码，或者读写了这个地址」。本次实际核对用的是 Capstone 反汇编，下面的地址也可以在 Ghidra 中逐个查看。 [Ghidra](https://github.com/NationalSecurityAgency/ghidra)

## 3. 从橙羽织找到共用判定

从零定位时，先找一个你能主动改变的状态，比如来回装备橙羽织和另一件羽织。在测试存档里可以对照两种状态的内存读数，把候选值逐步缩小，再查看游戏从哪里读取候选地址。存档里的装备记录、内存里的当前装备和画面上的白光是三层信息，要分别核对。本次定位时，另一个存档工具中的 `ORANGE_ID = 0x01` 提供了线索，随后在反汇编里验证了运行时编号与白光分支的关系。

1. **从可观察的效果入手。** 橙羽织提供了一个能反复看到的信号。顺着羽织编号的读写查到 `0x7C3FD8` 一带，可以看到游戏比较 `[0x3CAF111]` 是否为 `1`。沿该分支继续走，白光查询在 `0x7C40C6` 调用 `0x407522`。
2. **检查是谁也在调用它。** `0x407522` 是一条跳转，实际函数在 `0x818E30`。它还有一个来自 `0x81A6B4` 的调用点。继续往上查会看到玩家攻击输入的处理路径，所以在 `0x818E30` 内动手，白光和直接一闪就能共用补帧结果。
3. **跟到真正的判定数据。** 在 `0x818E83`，游戏从敌人对象的 `+0x228C` 取出函数地址，随后调用这个函数。不同敌人可使用不同判定函数。以常见分支 `0x5923C0` 为例，它从敌人 `+0x30` 找到动画播放器，再读取播放器 `+0xB4` 的当前帧标志。它还会检查敌人状态、方向和距离。
4. **追踪谁写入该字段。** `0x5C9E34` 一带用当前帧索引查动画表，把读到的 32 位值写到 `+0xB4`。再看难度选择逻辑，就能确定当前难度下用哪一位判断直接一闪。标志位相当于同一个整数里的多个开关。代码用位掩码取其中一位。

| 游戏内部难度编号 | 逐帧表的一闪位掩码 |
| --- | --- |
| `0` | `0x00200000` |
| `1` | `0x04000000` |
| `2`、`3` | `0x00100000` |

想亲手复核时，可以在 Ghidra 跳到这几个地址，看 `call` 指向哪里、条件跳转改走哪条路。上面的地址是本机这版在反汇编里看到的虚拟地址。写进插件时用 **RVA**，也就是地址减去模块基址。这里基址是 `0x00400000`，例如挂钩点 `0x00818E89` 的 RVA 是 `0x00418E89`。运行时用游戏实际加载的基址加上 RVA。直接读取磁盘文件时，还要用 PE 节表把 RVA 换成文件偏移。 [Microsoft PE 格式说明](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format)

### 用资源验证推断

分析时先拆开敌人 `.ldt` 的 `LINK` 条目，找到 `0x0285` 或 `0x0286` 动作块。带 `CPK0` 头的块先解压，再根据动作目录和每条动作头中的偏移找逐帧标志数组。把同一难度的连续置位帧列出来，就能看到原始窗口宽度。比如 `em00.ldt` 的 `0x50` 号动作在难度编号 `1` 的有效帧是 `68`、`69` 两帧。

这里先确认数据，再编写补丁。仅凭一段指令或某只敌人的现象，很容易误以为所有类型都通过同一个字段表达状态。

想核对文件布局时，用十六进制查看器打开 `em00.ldt`。文件开头四字节是 `LINK`，本样本的条目从偏移 `0x08` 开始，每条 16 字节，依次是资源编号、数据偏移、块大小和附加字段。解压后，动作块开头的 32 位值是动作目录的槽位数，后面跟着各动作的相对偏移。动作头的前两字节是帧数。可以对照游戏在 `0x5C99E0` 一带读取帧数和解析帧表指针的过程，再按每帧 4 字节检查掩码。这里的多字节整数按小端序读取，低位字节放在前面。

### 初版漏掉多数敌人的原因

初版用播放器 `+0x94` 的动作指针来确认「这段动作有效」。单轨播放器会填写它。多轨播放器会从当前选中的轨道把帧表、帧索引和当前标志复制出来，`+0x94` 可以一直为空。看 `0x5CC490` 就能看到这些字段的复制。这样即使当前帧表有效，旧补丁也会提前返回。默认敌人配置表里的 51 项中，有 41 项使用多轨播放器。

修正版先从对象开头的虚函数表指针辨认多轨播放器，再用 `+0x1FC` 的当前轨道索引和 `+0x1F8` 的轨道总数判断是否有可用轨道。轨道有效后，两种播放器都从同步出的同一组字段读取帧表。这个问题是用敌人配置表和实际动作数据查出来的，所以测试要覆盖两种播放器。

## 4. 按这个顺序读补丁源码

| 从哪读 | 这部分做什么 |
| --- | --- |
| 第 103 行 `Field<T>` | 用「对象地址 + 偏移量」按指定类型取字段。`BYTE` 是 1 字节，`std::uint16_t` 是 2 字节，`std::uint32_t` 是 4 字节。这里的偏移来自反汇编。 |
| 第 110 行 `HasFrameTable` | 识别单轨和多轨播放器，按各自的方式检查当前动作。多轨的虚函数表地址由 `InitializeASI` 根据游戏基址计算。 |
| 第 52 行 `IsEarlierFrame` | 处理一张帧表。当前帧如果已经属于原窗口，交给游戏照常判定。否则找从当前帧往后最近的一段连续有效帧。该段结束的位置距离当前帧不超过阈值，才把当前帧算作新增帧。 |
| 第 128 行 `CheckIssen` | 读取难度和敌人动作，调用补帧算法。满足条件时，把掩码临时加到当前帧标志上，再调该敌人的原判定函数，返回后清掉刚加的位。原来的距离、方向与状态规则仍由敌人的函数执行。 |
| 第 166 行 `IssenCheckHook` | 用几条 x86 汇编把游戏现场接到 C++ 函数。把 `ESI` 中的敌人指针和 `EAX` 中的原回调地址放到 `ECX`、`EDX`，调用 `CheckIssen`。随后执行被覆盖的 `EDX` 读取，并跳回游戏。 |
| 第 179 行 `ReadMinimumFrames` | 找插件旁边同名的 `.ini`，读取 `[Issen]` 下的 `MinimumFrames`。缺失或无效时使用默认值 `0`。`0` 和 `1` 会跳过挂钩安装。 |
| 第 214 行 `InitializeASI` | 校验游戏的 PE 版本特征与挂钩点的原始指令。校验成功且启用补帧时，用跳转替换完整的 10 字节指令。 |
| 第 275 行 `DllMain` | DLL 加载时记录插件自身的模块句柄，以便找到 INI。实际安装挂钩由加载器调用 `InitializeASI` 完成。 |

动作播放器的四个核心字段是 `+0xA4` 的数组地址、`+0xC4` 的当前帧索引、`+0xC8` 的最后一个合法帧索引和 `+0xB4` 的当前标志。最后一个合法索引包含在动作里，所以查表前要判断索引是否越界。

用刚才的真实例子手算一次。`68–69` 的结束边界是 `70`，因为第 70 帧已经不在窗口中。阈值为 5 时，新起点是 `70 − 5 = 65`，因此 `65–67` 是新增帧。程序从当前帧算到结束边界，效果等价。窗口靠近动作开头时，最多补到第 `0` 帧。源码里的 `Timing` 和 `static_assert` 会在编译时检查这些边界。

`CheckIssen` 用 `__fastcall` 接收两个寄存器参数。它内部调用原函数时用 `__thiscall`，把敌人对象放进 `ECX`。这个函数原本位于游戏执行到一半的位置，因此挂钩要按原位置的约定恢复现场再跳回。 [Microsoft x86 `__fastcall`](https://learn.microsoft.com/en-us/cpp/cpp/fastcall?view=msvc-170) · [Microsoft x86 `__thiscall`](https://learn.microsoft.com/en-us/cpp/cpp/thiscall?view=msvc-170)

安装时，`VirtualProtect` 临时允许写入挂钩处的代码页。写好跳转后，`FlushInstructionCache` 刷新指令缓存，最后恢复旧页面保护。安装和补帧都在游戏进程内进行，重启时会重新检查配置。 [Microsoft `VirtualProtect`](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualprotect)

## 5. 编译和安装

1. 在 Visual Studio Installer 中准备 MSVC C++ Build Tools 和 Windows SDK。打开 **x86 Native Tools Command Prompt for VS 2022**，先打 `cl` 确认显示 x86 编译器。这段接口用到了 MSVC 的 x86 内联汇编。 [微软命令行构建指南](https://learn.microsoft.com/en-us/cpp/build/building-on-the-command-line?view=msvc-170) · [MSVC 内联汇编](https://learn.microsoft.com/en-us/cpp/assembler/inline/inline-assembler?view=msvc-170)
2. 在同一个命令提示符里进入仓库根目录，运行 `mkdir "%TEMP%\Oni3-Issen-Practice"`。接着用 `copy "src\Onimusha3.IssenWindow.cpp" "%TEMP%\Oni3-Issen-Practice\"` 复制源码，再用 `cd /d "%TEMP%\Oni3-Issen-Practice"` 进入练习目录。后面生成的编译文件都会放在这里。
3. 在同一个命令提示符里运行 `cl /nologo /W4 /WX /O2 /MT /LD /std:c++17 /EHsc /utf-8 /arch:IA32 Onimusha3.IssenWindow.cpp /link /OUT:Onimusha3.IssenWindow.asi /DYNAMICBASE /NXCOMPAT`。`/LD` 用来生成 DLL，`/MT` 把 C++ 运行库静态链接进插件，`/OUT` 决定产物名称。
4. 运行 `dumpbin /headers /exports Onimusha3.IssenWindow.asi`。预期会看到 `14C machine (x86)` 与导出函数 `InitializeASI`。编译练习成功后可以先停在这里。
5. 想测试自己编译的版本时，先退出游戏，把现用 ASI 备份到 `scripts` 之外，再把新 ASI 放到 `scripts\Onimusha3.IssenWindow.asi`。同一个补丁只保留一个正在加载的 `.asi`。配置继续用现有的 `scripts\Onimusha3.IssenWindow.ini`。撤回试验时，退出游戏并换回备份。

## 6. 验证、定位问题和继续练习

- **先看逻辑。** 可以手算 1 帧、2 帧、长窗口、空窗口、动作开头五种情况，再与 `static_assert` 对照。修正版还把本机资源里的 **2,471 段敌人动画**装进独立 x86 测试程序，检查不同难度和阈值下的返回值，并核对临时标志是否还原。
- **再看游戏。** 找剧情里能让橙羽织亮白光的敌人。保持同一个存档、难度、角色、站位和招式，分别设 `MinimumFrames=0` 和 `MinimumFrames=30`，每次都重启。先看白光是否提前，再用 `5` 测短窗口是否如预期。拿足轻做对照后，再对抡锤和滚地冲撞的敌人分别记录结果。
- **完全没变化。** 先核对 INI 文件名、`[Issen]` 段、阈值以及是否重启，再核对 ASI 是 x86、导出正确且在 `scripts` 目录。随后对照 `oni3.exe` 的哈希和挂钩处指令。这个版本在校验不通过时会直接返回。
- **只在部分敌人上有变化。** 记录敌人的招式、难度，以及原版是否亮白光。先查动画播放器类型和该招式在对应难度的逐帧标志，再看敌人回调里是否还有别的限制。本版覆盖按动作帧表标记的直接一闪窗口，个别独立脚本的机会需要沿它们自己的代码继续查。

第一次练习可以只把 INI 阈值改为 `3`，体验配置与代码各自负责什么。第二次在 `Timing` 里加一个你自己编的短窗口例子，手算哪几帧应被补上，再写一个 `static_assert` 验证。第三次回到反汇编，自己沿橙羽织的调用找到共用判定。以后做别的游戏机制，可以沿用这个次序，从一个可观察行为出发，追到数据，先做可验证的小改动，再扩大测试覆盖。
